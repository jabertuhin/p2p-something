The overall direction was strong, but the repository was **Phase 1 implemented, not yet
verified** — not Phase 0, and not ready for Phase 2.

## What was working well

- The roadmap introduces concepts incrementally.
- Whole-file transfer before block synchronization is the right learning sequence.
- Delaying vector clocks and CRDTs prevents premature abstraction.
- The Phase 2 sketch records decisions and explicitly defers future concerns.
- The single bidirectional TCP connection is a sensible two-peer starting model.
- `sbt test` compiles successfully and passes.

## What needed attention first

1. **The Phase 1 CLI is broken.** The sender branch reads `conf.receive.dir()` and
   `conf.receive.port()` instead of the sender options in `Main.scala`. The README demonstration
   therefore cannot currently work.

2. **The only test is the original `42 == 42` scaffold test.** The build is green, but none of the
   sync behavior is verified.

3. **The watcher migration is unfinished.** `util/Watcher.scala` constructs a new monitor, while
   `Sender.scala` still uses `WatchService`.

4. **The current protocol trusts the frame length and remote path.** Before allocating bytes or
   resolving a path, it should reject negative or oversized lengths, absolute paths, and normalized
   paths outside the sync root. This is useful protocol learning, not production polish.

5. **The repository guidance is stale.** `AGENTS.md` and `CLAUDE.md` still describe the repository as
   Phase 0. Update them after closing Phase 1 so future guidance starts from reality.

## Design observations that shaped Phase 2

Recorded here because they changed decisions, and the reasoning is worth keeping:

- **`directory-watcher` offers hash-based duplicate suppression, not a time-window debounce.** These
  are different mechanisms and the implementation notes conflated them.
- **A global `fs2` `.debounce` is unsafe on a watcher stream.** It can discard events for distinct
  files, or one half of a rename's delete/create pair.
- **A loopback guard that suppresses "the next event for this path" can discard a real local edit.**
  Specifically: receive remote update → write locally → user immediately edits the same path → the
  watcher fires. A naive guard eats the user's edit.
- **The accepted-version record must be updated by local writes too.** If only inbound events update
  it, an older remote event can overwrite a newer local write.
- **A delete must retain its `(timestamp, originator)` metadata.** That retained record is an
  in-memory tombstone even though the Phase 2 sketch calls the design "no tombstones". Removing both
  the file and its metadata permits stale resurrection.
